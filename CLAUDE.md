# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

LGU (General Mariano Alvarez, Cavite) social-assistance system: plain procedural PHP + MySQL (PDO), served by XAMPP. No framework, no build step, no test suite, no linter. Three assistance programs, identified everywhere by `assistance_type_id`: **1 = Medical, 2 = Burial, 3 = OPD** (outpatient vehicle scheduling).

## Running it

- Start Apache + MySQL from the XAMPP Control Panel; open `http://localhost/Resource_management/Resource_management/user/landingpage.php` (applicant portal) or `.../login/login.php` (admin/staff).
- DB: `lgu_assistance_system`, `root` with empty password (hard-coded in [config.php](config.php)). Fresh install: import [database/lgu_assistance_system.sql](database/lgu_assistance_system.sql) (it already includes the person-rules and Disapprove schema; no migration needed). Existing DB: apply `migration_fix_schema.sql`, `migration_person_rules.sql`, `migration_disapprove.sql` via phpMyAdmin, in that order; all are safe to re-run (each file's header explains what it does; `_cleanup`/`_rollback` are optional follow-ups to the disapprove migration). Until `migration_person_rules.sql` is run, Medical/Burial applications are still accepted but without the person checks (`person_rules_installed()`), and admin pages show a "Database update needed" banner.
- `composer install` for `google/apiclient` (Google sign-in) and `phpmailer/phpmailer` (approval emails). `vendor/autoload.php` may be missing locally. On Windows, unpacking `google/apiclient-services` can exceed Composer's 300 s limit: set `COMPOSER_PROCESS_TIMEOUT=0`.
- Default admin: open [includes/admin_init.php](includes/admin_init.php) once (creates `admin` / `admin123`).
- Syntax-check a file: `C:\xampp\php\php.exe -l path\to\file.php`. Verification is otherwise manual in the browser.

## Architecture

**Every page `require_once '../config.php'`**, which starts the session, creates the global `$pdo`, aligns PHP's timezone with MySQL's `NOW()` (dates are stored with `NOW()`, so keep it that way), defines `app_base_url()`, and loads Google OAuth settings. Pages are flat scripts addressed by URL with relative `../` paths, so files must stay one directory below the project root.

**Two separate auth systems:**
- Admin/staff: `users` table, `login/login.php` sets `$_SESSION['user'] = [id, username, role ('admin'|'staff'), name]`; config.php mirrors the id to `$_SESSION['user_id']`.
- Applicants: `applicant_accounts` table, password or Google OAuth (`user/google_login_init.php` → `user/google_callback.php`), sets `$_SESSION['applicant']` (see `user/account_helpers.php`).

**Admin side** (`Main_dashboard/`, `medical/`, `burial/`, `opd/`, `reports/`, `staff/`): pages call `admin_layout_start([...])` / `admin_layout_end()` from [includes/admin_layout.php](includes/admin_layout.php), with UI building blocks in `includes/admin_components.php`, styles in `css/admin_ui.css`, behavior in `js/admin_ui.js`. Pages under `staff/` declare `define('UI_AREA', 'staff')` before loading the layout; OPD staff only handle program 3. `ADMIN_LAYOUT_REQUIRE_LOGIN` is `true`: every page using the layout requires an admin (staff pages: staff or admin) and redirects others to the sign-in page. Staff/admin accounts are created only by a signed-in admin via `login/register.php` ("Add staff account"); it's open only while no admin exists (first-admin bootstrap). CDN libraries (Chart.js, SweetAlert2) are declared in `ui_vendor_libs()` with SRI hashes and local fallbacks in `js/vendor/`.

**Approve/Disapprove must go through [includes/application_decision.php](includes/application_decision.php)** (`decide_application()`, `decision_run_endpoint()`, `decision_save_update_form()`). It enforces role (admin for all, staff for OPD), CSRF (`decision_csrf_field()`), Pending-only transitions with row locking, writes `application_status_history`, and on Disapprove "releases" the person (undo Burial deceased flag, give back a Medical re-apply permission). Approving needs the approval details everywhere, including the Update pages (`decision_claim_parse()`, columns `applicant.claim_*` added by `decision_claim_ensure()` / `database/migrations/migration_approval_claim.sql`): Medical/Burial the amount (`decision_needs_amount()`) and where/date/time to claim; OPD the departure time (`OPD_DEPARTURE_DEFAULT`, 4:00 AM unless changed) and pick-up point, with the trip day = the patient's `checkup_date` (shown, not typed, so the staff schedule, daily report and email agree; `claim_date` stays NULL; a missing or past check-up date blocks approval, `decision_opd_schedule_problem()`); all the hard copies to bring and an optional note. Every Pending list (admin and staff OPD too) collects them in the Approve dialog (`ui_approve_dialog()`, `ui_claim_fields()`); after the commit, `decision_send_approval_email()` emails them (never the amount: the office doesn't put it in the email; it is still required in the dialog and saved) to the applicant's `applicant_accounts.email` via `includes/mailer.php` (PHPMailer, Gmail SMTP) and sets `approval_email_sent_at`. Walk-ins have no account, so no email. A failed email never undoes the approval: it comes back as `$result['warning']` → `$_SESSION['warning_message']` (stays on the page, not a toast). The staff dashboard and daily report show the departure (`ui_opd_departure()`). Status values: `Pending` / `Approved` / `Disapproved` (the old `Rejected` status is migrated away). Disapproved applications are excluded from all lists, counts and duplicate checks. Other admin forms that change data (walk-in add, edit, settings, register) also use `decision_csrf_field()`/`decision_csrf_ok()`; `edit_applicant.php` checks for an admin itself.

**Editing a record** (`Main_dashboard/edit_applicant.php`, admin only): every field of the program's form, grouped like the record view, checked with `validate_application()` (except the check-up date, which may be in the past for an old request). A stored value the admin doesn't change never blocks the save (older records have gaps), and only changed columns are written. The amount shows on Approved records (required for Medical/Burial, optional for OPD); the status is never changed here. A change to who a Medical/Burial application is for (patient name/birthdate; deceased name/birthdate/date of death) also corrects `beneficiaries` via `person_correct_identity()` (user/person_rules.php), under the person locks and in the same transaction; it is refused when that person is on other applications or would then match someone else on file. Each save is logged as `application_edited` (field names, plus the old → new amount).

`applicant.date_released` is not written or shown (it used to get the filing date, so it never meant the release date). List queries select `first_name`/`middle_name`/`last_name` and let `ui_person_name()` format them; don't `CONCAT()` a nullable middle name. Weekly groupings use ISO weeks computed in PHP (`date('o-W')`), not MySQL `WEEK()`.

**Admin tools** ([includes/admin_security.php](includes/admin_security.php), schema in `database/migrations/migration_admin_tools.sql`): the activity log (`activity_log()`, read by `Main_dashboard/activity_log.php` together with `application_status_history`, so Approve/Disapprove are not logged twice), the wrong-password limit at sign-in (5 wrong tries per username + address = 15 minute wait; `login_attempts`), `users.is_active` (an admin turns a staff account off in Admin settings > OPD staff; `decision_account_active()` signs a turned-off or removed account out on its next page) and `users.last_login_at`. Its tables/columns are created automatically by `admin_tools_ensure()` when the sign-in page or `admin_layout.php` loads (never mid-transaction, since DDL ends one), and every helper fails quietly if they are missing. `activity_log()` never throws; call it after a change succeeds. `Main_dashboard/export_applicants.php` is the CSV download behind the "Export CSV" button that `ui_type_tabs()` adds to every list (neutralises `= + - @` cells; keeps the contact number's leading zero).

**Live numbers**: [js/admin_live.js](js/admin_live.js) (loaded by `admin_layout_end()` on every admin/staff page) polls `Main_dashboard/live_counts.php` every 15 s while the tab is visible and rewrites the menu badges (`data-live-nav`, always printed, hidden at 0) and the dashboard's counts (`data-live`, `data-live-when`, `data-live-plural`, `data-live-card`). Same counting rules as the pages (waiting = Pending; all time = not Disapproved). The endpoint is read-only, answers staff with OPD only, returns 401 when signed out, and uses `session_abort()` so polling neither holds the session lock nor keeps an idle sign-in alive. To make another number live: print it with `data-live="<key>"` and add the key to the endpoint's JSON. Lists, charts and the year summary are not redrawn; the "new application" notice offers a Refresh.

**Applicant flow** (`user/`): program form (`Medical Assistance.php`, `burial_assistance_form.php`, `opdform.php`) → photo upload page (`medicaldoc.php` / `burialdoc.php` / `opddoc.php`, sharing `document_upload_page.php`) → `submit_assistance.php`, which saves the `applicant` row and files into `documents/`. Form data is carried between steps in `$_SESSION['<program>_form_data']`.
- [user/assistance_config.php](user/assistance_config.php) is the single source for per-program settings (`$ASSISTANCE_PROGRAMS`: required documents, prefill fields), upload limits, field length limits, choice lists (`BARANGAYS`, `MEDICAL_PURPOSES`, `OPD_REASONS`, `OPD_HOSPITALS`, `RELATIONSHIP_SUGGESTIONS`), and server-side validation (`posted_fields()`, `validate_application()`). Change required documents there, not in the pages.
- The admin dashboard's "Add walk-in applicant" form (templates in `Main_dashboard/dashboard.php`, behaviour in `js/admin_dashboard.js`, saved by `Main_dashboard/submit_admin_applicant.php`) mirrors the three online forms: same fields, same lists, same `validate_application()`, and for Medical/Burial the same person rules with `$accountId = null` ("the office": every Ref # shown, admin-facing messages). Change both sides together.
- [user/person_rules.php](user/person_rules.php): eligibility follows the *person* (name + birthdate with fuzzy Filipino-name normalization), not the account. Medical re-application needs an admin grant (`medical_reapply_decisions`, append-only log enforced by triggers, so never test grants on real data), given on the patient's approved Medical record (`ui_medical_reapply_panel()` → `medical/reapply_decision.php` → `decideMedicalReapply()`); Burial is one per deceased and marks them deceased in `beneficiaries`; OPD has no limits. Uses MySQL `GET_LOCK('lgu_person_<birthdate>')` (all Burial saves share `lgu_burial_same_name`), the same lock names as the disapprove path. The program "frequency" texts in `assistance_config.php` and the landing page FAQ describe these rules; keep them in sync.
- **Data privacy** ([includes/privacy.php](includes/privacy.php), notice at `user/privacy.php`): applicants must tick "I agree" on sign-up and at the upload step of every application (`privacy_consent_field()`, re-checked in `submit_assistance.php`); the date and notice version go to `applicant_accounts.privacy_accepted_at`/`privacy_version` (added by `ensure_user_schema()`). When the system starts collecting or sharing something new, update the notice text and `PRIVACY_NOTICE_VERSION`. The DPO's name/email in `PRIVACY_DPO` are for the office to fill in.
- **Satisfaction survey** ([includes/feedback.php](includes/feedback.php), table `feedback`, created by `feedback_ensure()`; `database/migrations/migration_feedback.sql`): one 1–5 rating + optional comment per decided application, given on the applicant's Feedback page (`user/feedback.php`, account menu; `view_application.php` links to it), saved by `user/feedback_submit.php`; not shown on the home page; admins see it in Reports > Client feedback (`reports/feedback_report.php`).
- **Claimant rule**: whoever fills in the form is the claimant. Burial: section 1 is the claimant; `petitioner_name` is the deceased. Medical: "For myself" saves `relationship = 'Self'` with the claimant columns copied from the patient (`medical_self_claimant()`); every view (`ui_applicant_record()`, `user/view_application.php`, the CSV export, the Medical report) shows a separate claimant only when it isn't Self (`ui_is_self_claimant()`), and the edit page has a "Who filed" choice instead of a typed "Self".
- **OPD companion is optional** (`petitioner_name` + `relationship` on OPD = who goes with the patient): both empty = the patient goes alone; one filled in needs the other (`opd_companion_errors()` in `assistance_config.php`, used by `opdform.php`, the walk-in submit and `edit_applicant.php`; `data-all-or-none` in `js/apply-form.js` does the same in the browser). Lists and views show `ui_opd_companion()` ("No companion").
- **Own age**: the applicant's own birthdate is `applicant_accounts.birthdate` (added by `ensure_user_schema()` v3; set in My Account → Profile, or kept from a Medical "For myself" application when empty; `account_own_birthdate()` falls back to that application's birthdate). `get_form_prefill()` returns it as `own` and fills the age of the person filling in the form (Burial claimant, Medical claimant, OPD patient when the name is theirs) as of today; `js/apply-form.js` does the same when the Medical choice or the OPD name changes (`data-own-*` on the form). Ages are not in `'remember'` (they go stale), and name/sex are copied from another program's application only when it was about the account holder (`application_is_about_holder()`).
- `user/application_eligibility.php`: account-level eligibility checks.
- `user/ai_chat.php`: Gemini-backed chat helper.

**Local secrets** live in private local files at the project root: `google_oauth.local.php`, `ai_chat.local.php` and `mail.local.php` (Gmail address + app password for the approval emails) (each returns an array; env vars `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_REDIRECT_URI`, `GEMINI_API_KEY`/`GEMINI_MODEL`, `MAIL_USERNAME`/`MAIL_PASSWORD`/`MAIL_FROM_NAME` override; each has a `.example` to copy). Don't inline credentials into code.

## Conventions

- PDO prepared statements everywhere; user-facing error messages are plain-language and never expose SQL (log details with `error_log`).
- Code comments explain the business rule in plain English; match that style.
- `zsetup_guideline/*.md` are older setup notes and partly stale (e.g. they reference `gmail_login.php`, which no longer exists, and a project path without the nested `Resource_management/`).
