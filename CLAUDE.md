# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

LGU (General Mariano Alvarez, Cavite) social-assistance system: plain procedural PHP + MySQL (PDO), served by XAMPP. No framework, no build step, no test suite, no linter. Three assistance programs, identified everywhere by `assistance_type_id`: **1 = Medical, 2 = Burial, 3 = OPD** (outpatient vehicle scheduling).

## Running it

- Start Apache + MySQL from the XAMPP Control Panel; open `http://localhost/Resource_management/Resource_management/user/landingpage.php` (applicant portal) or `.../login/login.php` (admin/staff).
- DB: `lgu_assistance_system`, `root` with empty password by default; override with `db.local.php` (copy `db.local.php.example`) or the `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASS` env vars, and never use root on a real server. Fresh install: import [database/lgu_assistance_system.sql](database/lgu_assistance_system.sql) (the COMPLETE current structure, checked table by table against the working database: person rules, Disapprove, approval details, admin tools, budget, announcements, feedback, password reset, pictures; no migration needed, and the pages then have nothing to create themselves). After changing the structure, regenerate it (the command is in its header) and keep the matching `ensure_*` helper and migration file; the helpers add a column through `schema_add_columns()` ([includes/schema.php](includes/schema.php)), never `ADD COLUMN IF NOT EXISTS` (MariaDB-only). Existing DB: apply `migration_fix_schema.sql`, `migration_person_rules.sql`, `migration_disapprove.sql` via phpMyAdmin, in that order; all are safe to re-run (each file's header explains what it does; `_cleanup`/`_rollback` are optional follow-ups to the disapprove migration). Until `migration_person_rules.sql` is run, Medical/Burial applications are still accepted but without the person checks (`person_rules_installed()`), and admin pages show a "Database update needed" banner.
- `composer install` for `google/apiclient` (Google sign-in) and `phpmailer/phpmailer` (approval emails). `vendor/autoload.php` may be missing locally. On Windows, unpacking `google/apiclient-services` can exceed Composer's 300 s limit: set `COMPOSER_PROCESS_TIMEOUT=0`.
- First admin: while no admin exists, `login/register.php` creates the first admin account (there is no default password); add staff afterwards from Admin settings. (The old `includes/admin_init.php`, which made `admin` / `admin123` for anyone who opened it, was removed: never add a page like it back.)
- Syntax-check a file: `C:\xampp\php\php.exe -l path\to\file.php`. Verification is otherwise manual in the browser.

## Architecture

**Every page `require_once '../config.php'`**, which starts the session, creates the global `$pdo`, aligns PHP's timezone with MySQL's `NOW()` (dates are stored with `NOW()`, so keep it that way), defines `app_base_url()`, and loads Google OAuth settings. Pages are flat scripts addressed by URL with relative `../` paths, so files must stay one directory below the project root.

**Two separate auth systems:**
- Admin/staff: `users` table, `login/login.php` sets `$_SESSION['user'] = [id, username, role ('admin'|'staff'|'aid_staff'), name]` (the `$dashboards` map there decides where each role lands after signing in, and must list every role or that role simply can't sign in); config.php mirrors the id to `$_SESSION['user_id']`. There is no picker at sign-in: `users.username` is unique, so the account's own `role` decides which dashboard opens (a `?role=` in the URL is ignored). `staff` is OPD staff; `aid_staff` is Medical & Burial staff (see Admin side, below). The sign-in and register pages are built on `css/admin_ui.css` (tokens, buttons, fields, alerts) plus `css/admin_login.css` (layout only), share the frame in [includes/auth_layout.php](includes/auth_layout.php) (inline icon sprite, navy side panel, `auth_alert()`), and use `js/admin_auth.js` (no Bootstrap, Font Awesome, GSAP or web font, so they work offline). They always render light (`data-theme="light"` on `<html>` switches off the dark-theme block); don't hard-code colours there.
- Applicants: `applicant_accounts` table, password or Google OAuth (`user/google_login_init.php` → `user/google_callback.php`), sets `$_SESSION['applicant']` (see `user/account_helpers.php`).

**Admin side** (`Main_dashboard/`, `medical/`, `burial/`, `opd/`, `reports/`, `staff/`): the per-program pages (overview, the four lists, record, Update; and the OPD staff copies of the lists, record and Update) are **one shared implementation**, [includes/program_pages.php](includes/program_pages.php) (`program_overview_page()`, `program_list_page($typeId, $page)`, `program_view_page()`, `program_update_page()`); each file under `medical/`, `burial/`, `opd/` and `staff/` is a stub of a few lines that calls it (staff stubs `define('UI_AREA', 'staff')` first), so the URLs stay and a fix is made once. Headings and wording are in `program_texts()`, columns in `program_columns()`. The Approve endpoints are `medical/approve_medical.php`, `burial/approve_burial.php`, `opd/approve_opd.php`, `staff/approve_opd.php` (used by the review page). Pages call `admin_layout_start([...])` / `admin_layout_end()` from [includes/admin_layout.php](includes/admin_layout.php), with UI building blocks in `includes/admin_components.php`, styles in `css/admin_ui.css` (colour tokens, light and dark), behavior in `js/admin_ui.js`. Pages under `staff/` declare `define('UI_AREA', 'staff')` before loading the layout; OPD staff (role `staff`) only handle program 3. `ADMIN_LAYOUT_REQUIRE_LOGIN` is `true`: every page using the layout requires an admin (staff pages: staff, aid_staff or admin) and redirects others to the sign-in page. Staff/admin accounts are created only by a signed-in admin: Admin settings > Add staff (the `create_staff` action of `Main_dashboard/admin_settings.php`) or `login/register.php`, both through `staff_account_create()` ([includes/admin_security.php](includes/admin_security.php): the same checks and the activity-log line); `register.php` is open to a visitor only while no admin exists (first-admin bootstrap). CDN libraries (Chart.js, SweetAlert2) are declared in `ui_vendor_libs()` with SRI hashes and local fallbacks in `js/vendor/`.

**Pages in a window** (the "Pages in a window" block of [includes/admin_layout.php](includes/admin_layout.php), [js/admin_pagemodal.js](js/admin_pagemodal.js), [js/admin_embed.js](js/admin_embed.js), the "A page in a window" block of css/admin_ui.css): **Admin settings** (menu item, the name chip in the top bar, Ctrl+K "Admin Settings" / "Add staff account", the dashboard's "Add staff account" button) and a staff member's **My account** open as a window in the middle of the page you are on, like the walk-in form, instead of replacing it. The window is `<dialog id="pageModal">` (printed by `admin_layout_end()` on every signed-in page) holding an `<iframe>` that loads the same address with `?embed=1`. A page takes part by passing `'embed_ok' => true` to `admin_layout_start()` (admin_settings.php, staff/my_account.php): with `?embed=1` it then draws only its own content (`ui_embedded()`: no menu, top bar, command bar or window; success messages stay on the page instead of a toast; `X-Frame-Options: SAMEORIGIN`), `admin_layout_end()` loads only admin_ui.js, admin_avatar.js and admin_embed.js, and `admin_ui.js` (config `embedded`) asks every confirmation in the page around the window (`confirmAction()` → `window.parent.confirmAction`), where there is room for it. The page reports the height of its content (`ResizeObserver` in admin_embed.js → `AdminPageModal.fit()`), so the window is exactly as tall as what is inside it (the screen's height at most; then the page scrolls inside, with its tab bar and its action bar kept in view): no empty space. Anything such a page redirects or links to must keep `?embed=1` (`$self()` in admin_settings.php; a hidden `embed` field in a form that posts elsewhere, like the picture form → `avatar_action.php`; `target="_top"` for a link that leaves, like the activity log); `ui_leave_to_login()` takes the whole tab to the sign-in page when the session ended while a window was open. A hidden `[data-embed-refresh]` marker (name saved, picture saved) makes the page behind reload when the window closes, so the top bar shows the change. The links keep their real address (`data-page-modal` from `ui_modal_attrs()` / `ui_modal_pages()`): Ctrl, Shift or the middle button, a bookmark, or no JavaScript opens the normal full page, which still works. In the window the Settings tabs are Profile / Password / Staff / Add staff / Applicants and the actions are a bar at the bottom (the buttons of the open tab; "Back to dashboard" is left out, the window has Close). To put another page in a window: add it to `ui_modal_pages()`, opt in with `embed_ok`, and keep its redirects and links inside with `?embed=1`.
**Medical & Burial staff** (role `aid_staff`): encode walk-in Medical and Burial applications (new ones and past paper records, past date allowed) for an admin to approve or decline; they never approve or disapprove, and the only place they see an amount is a single application's own record. They may fix their own mistake in a **Pending** application's details — same form as the admin's (`Main_dashboard/edit_applicant.php`, widened for this role: their two programs, status Pending only, re-checked once the record loads), Edit shown on the Pending list only (not Approved: a button nobody could use there is left off, not shown and refused) — but once an admin decides it, it locks again like everyone else's. Two permissions are kept apart: `decision_can($user, $typeId)` / `decision_roles($typeId)` (`includes/application_decision.php`) still say who may **decide** an application and stay admin-only for programs 1 and 2 (only `staff` is added, for program 3) — `aid_staff` is never in that list, on purpose. `staff_can_view($user, $typeId)` says who may merely **view** one (lists, record, read-only review, search, live counts): admin everything, `staff` program 3, `aid_staff` programs 1 and 2. Everywhere that used to assume "staff = OPD" for visibility (the `admin_layout.php` sign-in gate, `staff_nav()`, the Ctrl+K command bar, `Main_dashboard/search.php`, `live_counts.php`, `export_applicants.php`, `user/document.php`'s photo check, the review page's queue) now calls `staff_can_view()` instead. Their own pages live under `staff/` too, built the same way as OPD's on `program_pages.php` (`ui_types()[1|2]['staff_pages']`: `listmedical.php`/`Mpending.php`/`medicalapproved.php`/`medicaldisapproved.php`/`medicalwithdrawn.php`/`view_medical_applicant.php`/`Mupdate.php` and the Burial equivalents; `program_staff_guard()` sends the wrong staff role to "Page not found" rather than letting them see another program's pages), plus a combined `staff/aid_staff_dashboard.php` (Medical and Burial counts only) and `staff/aid_staff_report.php` (the admin's own Medical/Burial reports, `report_build($pdo, $f, true)`'s `$hideAmounts`, with every money figure left out: cards, amount columns, the budget table — which only ever appears on the Overview tab they don't have — the `.xlsx` from `reports/export.php` and the CSV from `export_applicants.php`). `staff/review.php` needs no separate copy: it is already read-only the moment `decision_can()` is false, which is exactly the `aid_staff` case. `staff_only_role()` (`admin_layout.php`) guards the handful of pages built for one specific staff role (both dashboards, both reports) the same way, so OPD staff and Medical & Burial staff can't open each other's.

A walk-in (`applicant.account_id` NULL) also records who keyed it in: `applicant.encoded_by` (users.id, NULL for an online application; set for every walk-in, an admin's too). Every Pending list (admin and staff) shows a Source column ("Online" or "Walk-in · name") with a `?source=online|walkin` filter (`ui_source_filter()`/`ui_source_query()`/`ui_source_cell()`), and the record view shows who encoded it next to when it was filed.

A Medical/Burial walk-in can be a past paper record that a staff member is only now encoding, already decided in person: the Approve dialog's (and the Update page's) "Already approved on paper?" date, walk-ins only, becomes `approved_at` instead of `NOW()` (`decision_backdated_approved_at()`, `$opts['backdated_approved_at']` in `decide_application()`), so Reports count it in the period it actually happened; no approval email is sent for one of these. Leaving it blank is a normal, same-day approval.

**Approve/Disapprove must go through [includes/application_decision.php](includes/application_decision.php)** (`decide_application()`, `decision_run_endpoint()`, `decision_save_update_form()`). It enforces role (admin for all, staff for OPD; Medical & Burial staff decide nothing, ever), CSRF (`decision_csrf_field()`), Pending-only transitions with row locking, writes `application_status_history`, and on Disapprove "releases" the person (undo Burial deceased flag, give back a Medical re-apply permission). Approving needs the approval details everywhere, including the Update pages (`decision_claim_parse()`, columns `applicant.claim_*` added by `decision_claim_ensure()` / `database/migrations/migration_approval_claim.sql`): Medical/Burial the amount (`decision_needs_amount()`) and where/date/time to claim; OPD no place or time (there is no pick-up point or departure time any more; `claim_place`/`claim_time`/`claim_date` stay NULL for new OPD approvals and old values are no longer shown), the trip day = the patient's `checkup_date` (shown, not typed, so the staff schedule, daily report and email agree; a missing or past check-up date blocks approval, `decision_opd_schedule_problem()`); all the hard copies to bring and an optional note. Every Pending list (admin and staff OPD too) collects them in the Approve dialog (`ui_approve_dialog()`, `ui_claim_fields()`); after the commit, `decision_send_approval_email()` emails them (never the amount: the office doesn't put it in the email; it is still required in the dialog and saved) to the applicant's `applicant_accounts.email` via `includes/mailer.php` (PHPMailer, Gmail SMTP) and sets `approval_email_sent_at`. Walk-ins have no account, so no email. A failed email never undoes the approval: it comes back as `$result['warning']` → `$_SESSION['warning_message']` (stays on the page, not a toast). The OPD approval details on the record, in the applicant's account and in the email are the trip day and the hard copies; the approved record shows them when `claim_requirements` is set (not `claim_place`, which OPD no longer has). **Disapproving needs a reason** the same way: the Disapprove dialog (`ui_disapprove_dialog()`, built-in dialog only, no SweetAlert) offers the tick-box reasons in `DISAPPROVAL_REASONS` plus a written "Other reason"; the Update page shows the same boxes (`ui_disapprove_reasons()`) when Disapprove is chosen, and its Remarks box is then the written reason. At least one is required (`decision_disapproval_compose()`, checked again in `decide_application()`, code `remarks`); they are saved as `disapproval_remarks`, one line each (so every list, report, CSV and applicant view keeps reading that one column; `user/view_application.php` and `user_notifications.php` show it with line breaks), and after the commit `decision_send_disapproval_email()` emails the lines to the applicant (`decision_email_recipient()` is the guard it shares with the approval email: walk-in, no address, mail not set up → `$result['warning']`, never an undone decision). Status values: `Pending` / `Approved` / `Disapproved` / `Withdrawn` (the applicant's own withdrawal, see below; the old `Rejected` status is migrated away). **People read "Declined"**: the word was changed everywhere it is shown (admin, staff, reports, CSV, emails, the applicant portal, which used to say "Not approved"), but the stored status value, the columns (`disapproved_at`, `disapproved_by`, `disapproval_remarks`), `DECISION_DISAPPROVED`, function names, URLs (`?status=Disapproved`, `report=disapproved`), file names and CSS classes keep "disapprove", so never rename those; a new status label uses `ui_badge()` (label "Declined") or maps `Disapproved` → `Declined` itself. Disapproved applications are excluded from all lists, counts and duplicate checks. Other admin forms that change data (walk-in add, edit, settings, register) also use `decision_csrf_field()`/`decision_csrf_ok()`; `edit_applicant.php` checks the sign-in itself: an admin, any record; Medical & Burial staff, their own two programs and only while still Pending (checked again once the record is loaded, after which it's "not found", not greyed out) — see Medical & Burial staff, below.

**Withdraw, edit and change documents by the applicant** ([includes/application_changes.php](includes/application_changes.php), migration `database/migrations/migration_application_changes.sql`, columns/CHECK/key added by `schema_application_changes_ready()` in includes/schema.php, called from config.php; `database/lgu_assistance_system.sql` already has them): only while the application is **Pending** and only by the account that owns it (anyone else gets "not found"); the same server checks everywhere: `application_owned()` / `application_change_problem()`. *Withdraw* (`user/withdraw_application.php` → `application_withdraw()`, button and optional reason on `user/view_application.php`): new status value `Withdrawn` (+ `applicant.withdrawn_at`, `withdrawal_reason`), CSRF, row lock + `WHERE status='Pending'`, a row in `application_status_history` with `changed_by` NULL, and the person is released like a decline (`decision_release_person($pdo, $app, 0, 'withdrawn by the applicant')`: Burial deceased flag undone, Medical re-apply permission given back by logging a new grant under the original grantor or the first admin); the applicant may file again at once; no email is sent for it; there is no un-withdraw. `Withdrawn` behaves like Disapproved in every rule and is **never** shown as Declined: every `status <> 'Disapproved'` became `status NOT IN ('Disapproved', 'Withdrawn')` (`ui_active_sql()`, lists, counts, live counts, trend, barangay map, reports, CSV, dashboard; duplicate and person rules already used positive `IN ('Pending','Approved')`; the Burial `person_rule_key` and `chk_applicant_status` were rebuilt in one ALTER). The admin side has a **Withdrawn tab per program** (`medical/medical_withdrawn.php`, `burial/burial_withdrawn.php`, `opd/opd_withdrawn.php`, `staff/opdwithdrawn.php` → `program_list_page($t, 'withdrawn')`, count on the tab, reason shown, record view shows "Withdrawn by the applicant"); a decision on an application that was withdrawn while open is refused with "The applicant withdrew this application" (`decision_not_pending_text()`); the Update page and review page say so too; the activity log shows `application_withdrawn` (actor "Applicant: name"). *Edit* = the three online forms in edit mode (`?edit=<id>`, `application_edit_context()` / `application_edit_save()`): same validation, person rules with the application's own id left out (OPD one-per-day under the day lock; a Medical/Burial identity change goes through `person_correct_identity(..., $forApplicant = true)`: no Ref #s in the messages, "call the office" instead, and the applicant's own declined/withdrawn applications don't count as "other applications"), only changed columns written, `created_at` untouched (the application keeps its place in the queue), `edited_at` / `edit_count` set, `updated_at DATETIME(6)` is the optimistic-concurrency version carried in the form (a change by the office or another tab since the page opened is refused). `user/edit_documents.php` changes the photos with `application_read_uploads()` (shared with `submit_assistance.php`: real JPG/PNG/WEBP content, 3 per requirement, 10 MB) and `application_documents_save()` (every requirement keeps ≥1 photo, rows and files change together, old files are deleted only after the commit); `js/apply-upload.js` runs it in edit mode (`data-edit="1"`). The office sees "Edited by the applicant" on the record, the review page and an **Edited** tag on the Pending/All lists (`ui_status_cell()`); the edit is logged as `application_edited` (role `applicant`). An applicant can never change the program, status, account, amount or approval/claim columns this way. Not built: an un-withdraw, a live notice for "application edited", a warning to the office when something is edited while its review page is open (it only shows the tag on the next load).
**Editing a record** (`Main_dashboard/edit_applicant.php`, admin any record; Medical & Burial staff their own two programs, Pending only, from the Pending list's Edit button — see Medical & Burial staff, above): every field of the program's form, grouped like the record view, checked with `validate_application()` (except the check-up date, which may be in the past for an old request). A stored value the editor doesn't change never blocks the save (older records have gaps), and only changed columns are written. The amount shows on Approved Medical/Burial records only (required; OPD gives no money, so its edit page has no amount box and ignores a posted one) — so a Medical & Burial staff edit never has it, Pending having none yet; the status is never changed here. A change to who a Medical/Burial application is for (patient name/birthdate; deceased name/birthdate/date of death) also corrects `beneficiaries` via `person_correct_identity()` (user/person_rules.php), under the person locks and in the same transaction; it is refused when that person is on other applications or would then match someone else on file. Each save is logged as `application_edited` (field names, plus the old → new amount).

`applicant.date_released` is not written or shown (it used to get the filing date, so it never meant the release date). List queries select `first_name`/`middle_name`/`last_name` and let `ui_person_name()` format them; don't `CONCAT()` a nullable middle name. Weekly groupings use ISO weeks computed in PHP (`date('o-W')`), not MySQL `WEEK()`.

**Admin tools** ([includes/admin_security.php](includes/admin_security.php), schema in `database/migrations/migration_admin_tools.sql`): the activity log (`activity_log()`, read by `Main_dashboard/activity_log.php` together with `application_status_history`, so Approve/Disapprove are not logged twice), the wrong-password limit at sign-in (5 wrong tries per username + address = 15 minute wait; `login_attempts`), `users.is_active` (an admin turns a staff account off in Admin settings > Staff; `decision_account_active()` signs a turned-off or removed account out on its next page) and `users.last_login_at`. Its tables/columns are created automatically by `admin_tools_ensure()` when the sign-in page or `admin_layout.php` loads (never mid-transaction, since DDL ends one), and every helper fails quietly if they are missing. `activity_log()` never throws; call it after a change succeeds. `Main_dashboard/export_applicants.php` is the CSV download behind the "Export CSV" button that `ui_type_tabs()` adds to every list (neutralises `= + - @` cells; keeps the contact number's leading zero).

**Reports** (`reports/reports.php`, admin only; engine in [includes/report_data.php](includes/report_data.php)): `report_filters($_GET)` checks the filters (tab: Overview / Medical / Burial / OPD / Disapproved / Client feedback; period: year, quarter, month, week or From–To dates), `report_build()` loads the builder for the tab (`reports/overview_report.php`, `program_report.php` for Medical and Burial, `opd_report.php`, `disapproved_report.php`, `feedback_report.php`; each is one function returning cards, charts and tables) and `report_render()` draws it. All queries are prepared; periods are `col >= from_dt AND col < to_dt`. **Which date**: approved applications and money always count by `approved_at` (older records fall back to `created_at`); there is no "count by date filed" choice (removed; `?basis=` in an old address is ignored); Pending always counts by the filing date; Disapproved only appears on its tab (by `disapproved_at`). Days go into chart columns (day / ISO week / month) in PHP (`report_buckets()`), never MySQL `WEEK()`. **Excel**: `reports/export.php` writes the same `$model['tables']` as a real `.xlsx` (`includes/xlsx_writer.php`, no zip extension needed): a Summary sheet plus one sheet per table, same columns as the page but nothing cut short, contact numbers as text, amounts and counts as numbers; only tables with `export => true` are written (not the chart figures or the decision-time table), and a long Overview's people lists (`screen => false`) are file-only. It is logged as `export_report`. **Claimant**: Burial's claimant is the person on the form; Medical "For myself" has no separate claimant (claimant cells show "—", the patient's own columns hold their details), same rule as the record view and CSV (`report_claimant()`). **Budget**: the Overview's "Budget use" table reads the budget from the Budget page (below) and links to it. Printing uses `.print-head` / `.print-sign` and a landscape named page (`.report-section`).

**Budget** ([includes/budget.php](includes/budget.php), page `Main_dashboard/budget.php`, admin only, menu item "Budget"; tables `budget_entries` / `budget_overrides` created by `budget_ensure()`, `database/migrations/migration_budget.sql`): the yearly budget of Medical and Burial (OPD gives no money). It is a ledger: an admin sets a program's starting budget for the current or next year, then can add to it, reduce it, **correct** it (type the right total, for a wrongly typed figure) or **remove** it (the program has no budget again, e.g. set for the wrong program or year), each with a reason (`budget_record()`); a reduction or correction can't go below what is already approved. Rows are never edited or deleted: a correction or removal is a new row (kinds `start` / `add` / `reduce` / `correct` / `remove`), so the history shows what was declared before, who changed it and why; the budget is the replay of the rows in order (`budget_replay()`). Only the current and next year can be changed. "used" is not stored, it is the sum of Approved amounts counted by `approved_at` (fallback `created_at`), the same figure the Reports call released (`budget_statuses()`; states none / ok / warn from `BUDGET_WARN_PERCENT` = 80% / over). **Approving is checked on the server inside `decide_application()`**, under `GET_LOCK('lgu_budget_<type>')` so two admins can't both take the last pesos: no budget set = no limit; it fits = approved (at 80%+ the message says how much is left); it would go over = refused with code `budget` unless a `budget_reason` is sent, and then it is approved and saved in `budget_overrides` in the same transaction (an over-budget approval is allowed on purpose, with a paper trail: urgent aid must not be blocked). A budget table that can't be read never stops an approval (fails open, logged). The Approve dialog and the Update page show the remaining budget under the amount (`ui_budget_note()`, `updateBudgetNote()` in admin_ui.js) and reveal the reason box when the typed amount passes it. The budget also shows on the dashboard and the Medical/Burial overview pages (`ui_budget_panel()`). Activity log: `budget_start` / `budget_add` / `budget_reduce` / `budget_correct` / `budget_remove` / `budget_override`. Not built yet: warning banner/email, effect of an Edit-record amount change on the budget, per-approval limits, quarterly allotments, committed vs paid.

**Live numbers**: [js/admin_live.js](js/admin_live.js) (loaded by `admin_layout_end()` on every admin/staff page) polls `Main_dashboard/live_counts.php` every 15 s while the tab is visible and rewrites the menu badges (`data-live-nav`, always printed, hidden at 0) and the dashboard's counts (`data-live`, `data-live-when`, `data-live-plural`, `data-live-card`). Same counting rules as the pages (waiting = Pending; all time = not Disapproved). The endpoint is read-only, answers each staff role with only the programs `staff_can_view()` gives it (OPD staff: OPD; Medical & Burial staff: Medical/Burial), returns 401 when signed out, and uses `session_abort()` so polling neither holds the session lock nor keeps an idle sign-in alive. To make another number live: print it with `data-live="<key>"` and add the key to the endpoint's JSON. Lists, charts and the year summary are not redrawn; the "new application" notice offers a Refresh.

**Trend lines and count-up**: `trend_daily_new()` ([includes/trend.php](includes/trend.php)) gives the last 14 days of new applications per program (not Disapproved); `ui_sparkline()` draws them in PHP and `js/admin_live.js` redraws them with the same arithmetic (keep `ui_spark_geometry()` and `sparkGeometry()` identical); `live_counts.php` also returns `days`/`daily`. Numbers count up (700 ms, not when the computer asks for less motion) and flash once when they change; a screen-reader sentence is kept in `[data-live-announce]` (the panel itself is not `aria-live`).

**Barangay heat map** ([includes/barangay_map.php](includes/barangay_map.php)): the dashboard's "Applications by barangay" tiles, one per official `BARANGAYS` name, one blue in at most 5 steps with the number printed on every tile. It is a grid, not a geographic map (there is no boundary data; give a tile a place with `BARANGAY_MAP_POSITIONS`). ## Conventions

- **Decline reason picker**: the shared decline dialog and Update page use a closed `<details>` picker; clicking Reason reveals the preset choices and an "Other reason" checkbox. Checking Other reveals a required explanation; unchecking it hides and disables the explanation so its draft is not submitted. `decision_disapproval_compose()` also rejects an empty explanation when `other` is selected. Only the explanation text, not the word "Other", is saved with the selected preset sentences in `disapproval_remarks`.
- **New approval amount**: Medical/Burial approval fields in `ui_claim_fields()` accept whole pesos; the custom arrows and keyboard Up/Down in `js/admin_ui.js` change the current value by ₱100. `decide_application()` rejects fractional amounts on approval. Existing records and budget ledger values retain their stored precision.
- **Approved Medical/Burial amounts**: both Approved lists omit `.00` from whole-peso amounts and their total (`trim_zero_decimals` on the amount column). Their shared Edit record page also uses the ₱100 arrows, shows whole amounts without `.00`, and accepts whole-peso corrections. An unchanged older fractional amount is preserved; lists still show its cents accurately.

- **Closed folders and files** (root `.htaccess`, plus `.htaccess` in `includes/`, `database/`, `zsetup_guideline/`, `documents/`, `avatars/`, `staff_avatars/`): `.git`, `vendor`, `database`, `includes`, `*.md`, `*.sql`, `*.json`, `*.local.php` and the upload folders are never served by address. Photos go through `user/document.php`, applicant pictures through `user/avatar_file.php?f=` (owner or signed-in office only), staff pictures through `Main_dashboard/avatar.php`. A new folder of code or private files gets its own `.htaccess` the same way. Uploaded files (`documents/`, `avatars/`, `staff_avatars/`, `announcement_images/`) are gitignored: never commit them.
- **Errors never go to the screen**: `config.php` turns `display_errors` off (set `APP_DEBUG` to `1` in the environment or `db.local.php` on your own computer to see them) and shows a plain message for an uncaught exception; the details are in the PHP error log. The database connection is `utf8mb4` like the tables. Sessions use strict mode (`includes/session_start.php`).
- **OPD "reason for the check-up"** is the column `applicant.checkup_reason` (it was `diagnosis`; the program itself is still named "Outpatient Diagnosis"). An older database is renamed by `schema_checkup_reason_ready()` (includes/schema.php), called from `config.php` on the first page after the update (answers kept; `database/migrations/migration_checkup_reason.sql` does it by hand; `database/lgu_assistance_system.sql` already has the new name). The field name is `checkup_reason` in the forms, walk-in, edit page, lists, reports, CSV and Excel; label it "Reason for check-up", never "Diagnosis". **Burial has no purpose/reason**: the Burial forms never asked for one, and it is no longer shown on the record, the edit page, the CSV or the Burial report/Excel (the old `applicant.purpose` values stay in the table, unused); Medical keeps its "Purpose".
- **Service area is fixed**: municipality and province are always General Mariano Alvarez, Cavite (`SERVICE_MUNICIPALITY` / `SERVICE_PROVINCE`): the forms show them locked and `force_service_area()` puts them back on the server (online forms, walk-in). Old records keep what they have; Edit record doesn't force it.
- **Office accounts are never deleted once they decided or encoded something**: Admin settings > Staff removes a staff account only if it has no approvals, declines, status history or encoded walk-ins (`staff_has_records()`, which also checks `applicant.encoded_by`), because removing it would erase who approved a payment or keyed in a walk-in; otherwise "Turn off access". Other administrators can be turned off there too (`toggle_admin`; never your own account).
- **Office passwords** (admin and staff): 8+ characters with letters and numbers, checked by `staff_password_problem()` (`includes/admin_security.php`). A session carries `$_SESSION['user']['pwv']`, a fingerprint of the password hash (`account_password_mark()`); `decision_account_active()` ends the sign-in when it no longer matches, so a changed or reset password signs the account out everywhere else.
- **Forgot password for the office** ([includes/office_password_reset.php](includes/office_password_reset.php); pages `login/forgot_password.php`, `login/reset_password.php`, `login/verify_email.php`; tables `user_password_resets` / `user_email_verifications` and `users.email_verified_at`, made by `office_reset_ensure()`, `database/migrations/migration_office_password_reset.sql`, already in `database/lgu_assistance_system.sql`): the sign-in page's "Reset it by email". Same shape as the applicants' flow (`includes/password_reset.php`) but a separate table and stricter: a reset link goes **only to a confirmed email** (the owner opens a link we email when the address is saved: a mistyped address must never be able to take over an admin account); the link works once and expires after `OFFICE_RESET_MINUTES` (30); a turned-off account gets nothing; 3 links/hour per account, 10/hour per address; the page answers the same whatever happens (`password_reset_finish_response()`). Saving a new password ends every other sign-in of that account (the `pwv` fingerprint) and lifts the wrong-password wait; the old address and the new owner are told by email. **Only Admin accounts have an email and can reset by email; staff (OPD, Medical & Burial) have none** and an admin resets their password in Admin settings > Staff (every `office_reset_*` query is limited to `role = 'admin'`, and `staff_account_create()` ignores an email for a staff role). An Admin account **must have an email** (`staff_account_create()`'s `$email`, in Admin settings > Add staff and `login/register.php`, where the box shows only while Admin is chosen). An admin sets or changes their own in Admin settings > Profile: changing it needs the current password, clears the confirmation, and the tab offers "Send the confirmation email again". Activity log: `password_reset_sent` / `password_reset_failed` / `password_reset_done` / `email_confirmed` (addresses are masked, `office_mask_email()`).
- **Google sign-in** matches an account by `username = email` only when it holds a Google token, or by a *confirmed* email; My Account refuses a new username containing `@`; a password account that squats an email-shaped username is renamed (`user<id>`) when that email's real owner signs in with Google (`user/google_callback.php`).
